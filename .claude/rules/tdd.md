# TDD Rule

> **이 규칙은 Rigid다 — 상황에 맞게 변형하지 마라.** "이번만 예외로"는 예외 사유가 되지 않는다.

## 0. 우선순위 조항

이 파일은 **기본값(fallback)**이다. 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시돼 있다면 **그쪽이 우선**하고, 이 파일은 무시한다. 프로젝트 규칙이 없거나 침묵할 때만 이 파일을 적용한다.

## 1. 적용 기준

### TDD 필수 적용 대상

- **비즈니스 로직** (계산, 상태 전이, 도메인 규칙)
- **API 핸들러/엔드포인트** (요청·응답, 인증/인가 분기 포함)
- **유틸리티 함수** (순수 함수, 변환/파싱/포맷팅 로직)
- **버그 수정** (수정 전 반드시 실패하는 재현 테스트부터 작성)

### TDD 불필요 대상

- **타입 정의** (interface, type alias)
- **설정 파일** (config, env, build 스크립트)
- **순수 UI 마크업** (로직 없는 프레젠테이션 컴포넌트, 스타일)
- **SQL / 마이그레이션 스크립트**

판단이 애매하면 "이 코드가 잘못된 값을 반환하거나 잘못된 상태를 만들 수 있는가"로 묻는다. 그렇다면 필수 대상이다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 욱여넣지 않는다.
- 테스트 작성 후 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유는 반드시 **"기능 미구현"**이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED로 인정하지 않는다.

### GREEN

- 테스트를 통과시키는 데 **필요한 최소한의 코드만** 작성한다 (**YAGNI**).
- 아직 요구되지 않은 케이스를 미리 처리하지 않는다.
- **신규 테스트와 기존 테스트 전체가 통과**하는지 확인한 뒤에만 다음 단계로 넘어간다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 수행한다.
- 리팩터링 전체 구간 동안 **테스트는 계속 green을 유지**해야 한다.
- 이 단계에서 **새로운 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED로 넘긴다.

### 반복

- REFACTOR가 끝나면 **다음 동작에 대한 RED로 되돌아간다.** 사이클을 건너뛰지 않는다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다는 사실을 인지한 순간, **그 코드는 삭제하고 RED부터 다시 시작**한다.
- "일단 짜둔 거 참고용으로 남긴다"는 **금지**한다. 주석 처리, 별도 파일 보관, `_old` 접미사 등 어떤 형태로도 남기지 않는다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | **단순한 코드일수록 테스트 작성 비용도 낮다.** 복잡도가 낮다는 것이 생략 이유가 되지 않으며, 단순한 코드도 리팩터링 중 깨진다. |
| "나중에 추가하겠다" | **나중은 오지 않는다.** GREEN 이후엔 컨텍스트가 사라지고, 다음 기능 압박에 밀려 영구히 누락된다. |
| "시간이 없다" | **TDD는 디버깅 시간을 줄여서 갚는다.** 테스트 없이 짠 코드는 리뷰·디버깅·회귀 확인에 더 많은 시간을 쓰게 만든다. 지금 아낀 시간은 이자를 붙여 돌려받는다. |
| "삭제하면 낭비" | **검증되지 않은 코드는 자산이 아니라 부채다.** 먼저 짠 코드가 옳다는 근거는 테스트 통과뿐이며, 그 근거 없이 남기는 것 자체가 낭비다. |
| "프로토타입이다" | **프로토타입은 별도로 명시하고 격리한다** (예: `/prototype`, `/spike` 디렉토리, PR에 명시). 격리 없이 본 코드베이스에 섞이면 이 규칙이 그대로 적용된다. |
