# commit: 컨벤션에 맞는 커밋 생성

작업 디렉토리의 변경사항을 분석해 의미 있는 단위로 나누고, 이 저장소의 커밋 컨벤션에 맞는 메시지를 작성해 **승인을 기다리지 않고 바로 커밋**한다.

## 워크플로우

### Step 1: 변경사항 분석

- `git status`로 변경/추가/삭제된 파일 전체 목록을 확인한다.
- `git diff`(스테이지 안 된 변경)와 `git diff --staged`(스테이지된 변경)로 실제 내용을 확인한다.
- 시크릿·자격증명이 의심되는 파일(`.env`, `credentials.json` 등)이 포함돼 있으면 사용자에게 알리고 제외를 제안한다.

### Step 2: 논리적 단위로 분류

- 변경사항을 하나 이상의 논리적 커밋 단위로 묶는다. 서로 관련 없는 변경(예: 기능 추가 + 무관한 오타 수정)은 별도 커밋으로 분리를 제안한다.
- 각 단위가 다음 중 어떤 성격인지 판단한다: 신규 기능(`feat`), 버그 수정(`fix`), 리팩터링(`refactor`), 빌드/설정/잡무(`chore`), 문서(`docs`), 테스트(`test`).
- `git log --oneline -20`으로 최근 커밋 스타일을 참고해 일관성을 맞춘다(이 저장소는 `type: 한국어 요약` 또는 `type(scope): 한국어 요약` 형식을 사용해왔다).

### Step 3: 한국어 커밋 메시지 작성

형식: `type(scope): 요약` 또는 `type: 요약` (scope는 선택, 있으면 작업 영역을 짧게 표기)

- 요약은 한국어로, 무엇을 바꿨는지가 아니라 **왜** 바꿨는지가 드러나게 간결히 쓴다(diff만 봐도 알 수 있는 내용은 반복하지 않는다).
- 첫 줄은 간결하게 유지하고, 추가 설명이 필요하면 본문에 줄바꿈 후 작성한다.
- 여러 단위로 나뉘었다면 단위별로 메시지 초안을 각각 제시한다.

### Step 4: 승인 없이 바로 커밋

- 승인을 묻지 않고 단위별로 관련 파일만 `git add`한 뒤 즉시 커밋한다(`git add -A`/`git add .`처럼 전체를 한 번에 올리지 않는다).
- 커밋 전, 스테이지된 파일 목록에 시크릿·자격증명이 의심되는 파일이 없는지 마지막으로 한 번 더 확인한다(Step 1에서 발견됐다면 제외하고 진행한다).
- 커밋 메시지는 항상 HEREDOC으로 전달해 포맷을 보존한다.
- 여러 논리 단위로 나뉘었다면 단위마다 순서대로 `git add` + 커밋을 반복한다.
- 커밋 완료 후 각 커밋의 해시와 메시지, `git status` 결과를 사용자에게 보고한다(사전 승인은 없지만 결과 공유는 항상 한다).
- 사용자가 명시적으로 요청하지 않는 한 push는 하지 않는다.

## 주의사항

- 사용자가 먼저 커밋을 요청하지 않는 한 이 스킬을 스스로 실행하지 않는다.
- `--no-verify` 등으로 훅을 건너뛰지 않는다. 훅이 실패하면 원인을 파악해 수정 후 다시 커밋한다.
- 기존 커밋을 `--amend`하지 않는다(사용자가 명시적으로 요청한 경우만 예외).
- 빈 변경사항이면 빈 커밋을 만들지 않고 그 사실을 알린다.
- 시크릿으로 의심되는 파일이 있으면 자동 커밋을 멈추고 사용자에게 먼저 확인받는다(승인 생략은 일반 커밋 절차에만 적용되고, 시크릿 의심 시에는 예외로 확인을 거친다).
